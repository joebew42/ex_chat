# Improve assertions on received messages in websocket_acceptance_test.exs

GitHub Issue: https://github.com/joebew42/ex_chat/issues/18

## Context

The WebSocket acceptance tests live in `test/ex_chat/web/websocket_acceptance_test.exs`
(the issue refers to it as `websocket_test.exs`). Text frames received from the
server are forwarded to the test process as raw JSON strings by the
`WebSocketClient` / `PingAwareWebSocketClient` helpers in `test/test_helper.exs`.

Assertions today are written as `assert_receive` with a hard-coded literal JSON
string, e.g.:

```elixir
assert_receive "{\"room\":\"default\",\"message\":\"welcome to the default chat room, a-user!\"}"
```

## Problem

`assert_receive/3` expects its first argument to be a **pattern**, not an
arbitrary expression. This means the expected message cannot be built from a
function call (e.g. `Poison.encode!/1`) or an interpolated variable — you are
forced to inline an exact literal string. The consequences:

- **Brittle**: the assertion depends on the exact JSON key ordering produced by
  the serializer. Any change to how the payload is encoded breaks the test even
  though the semantic content is unchanged.
- **Hard to read**: escaped JSON strings are noisy and easy to get subtly wrong.
- **Not composable**: dynamic values (usernames, room names) cannot be
  interpolated cleanly into the expected value.

## Goal

Make assertions on received messages robust and readable by asserting on the
**decoded content** of the message rather than on an exact serialized string.
The pattern is: bind the received raw message with a pattern, then decode it
and assert on the resulting map (which may be built with variables/functions).

## Plan

1. **Add a test helper** in `test/test_helper.exs` (or the test module) to make
   the intent explicit and reusable, e.g. a small helper that receives the next
   text frame and returns its decoded map, or an `assert`-style helper that
   decodes and compares. Sensible default:

   ```elixir
   # captures the next forwarded text frame and decodes it
   assert_receive raw_message when is_binary(raw_message)
   assert Poison.decode!(raw_message) == %{
     "room" => "default",
     "message" => "welcome to the default chat room, a-user!"
   }
   ```

   A shared helper (e.g. `assert_receive_message(expected_map)`) can wrap the
   `assert_receive` + `Poison.decode!` + comparison so each test reads as a
   single expressive line.

2. **Refactor every `assert_receive`** on a JSON payload in
   `websocket_acceptance_test.exs` to assert on the decoded map instead of the
   literal string. Covers the welcome-message, send-message, error, create-room,
   join-room, and connect-with-token tests.

3. **Preserve the special cases** that are already pattern-based and should stay
   as patterns:
   - `refute_receive _` (invalid message / invalid command tests)
   - `refute_receive <literal>` in the "join twice" test — update to match the
     new decoded-assertion style where a positive assertion is involved, keeping
     the refutation semantics intact.
   - `assert_receive {:ping_received, _payload}, 1_000` — already a proper
     pattern, leave unchanged.

4. **Keep the HTTP `post_json` tests unchanged** — they already decode with
   `Poison.decode!` and assert on maps; they are the model this refactor follows.

## Acceptance Criteria

- No `assert_receive` in the WebSocket acceptance test asserts against a
  hard-coded escaped JSON string for its payload.
- Assertions compare against decoded maps, so they are independent of JSON key
  ordering.
- All existing test scenarios remain covered and the suite passes
  (`mix test test/ex_chat/web/websocket_acceptance_test.exs`).
- The refactor touches test files only (commit prefix `test:`).

## Out of Scope

- Changing production code / message serialization.
- Changing the ping/pong assertion, which is already a proper pattern.

      received text frame, independent of JSON key ordering.
- [x] Added `refute_receive_message/2` helper — decode-based refutation for the

### Key decisions

- **Selective matching was required.** The original `assert_receive "<literal>"`
  matched *selectively*: it scanned the mailbox for that exact frame, skipping
  interleaved frames (e.g. a `welcome` broadcast before a message echo, or a
  `success` before an `error`) and tolerating out-of-order delivery — the
  `error` reply can arrive before the broadcast `welcome`. The naive
  "decode the first frame" helper suggested in the plan broke on this. The
  helpers therefore match selectively on decoded content and re-queue any
  skipped frames so later assertions can still consume them.
- Suite is green and stable across repeated runs
  (`mix test test/ex_chat/web/websocket_acceptance_test.exs`, 18 tests; full
  suite 45 tests).

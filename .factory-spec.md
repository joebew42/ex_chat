# ex_chat — Greet a joining user with how close Christmas is

**Epic:** christmas-countdown-greeting · **Item:** chat-christmas-greeting
**Repo:** ex_chat (`~/workspace/ex_chat`, branch from `master`)
**App:** n/a — single-application repo, no monorepo

## What this repo must do

ex_chat already greets a joining user privately with
`welcome to the <room> chat room, <user>!`, composed inline in the join use case
and delivered over the user's existing WebSocket session. This item **appends a
seasonal clause** to that greeting: a countdown on an ordinary day, a Christmas
Day greeting on 25 December, and a shopping reminder from 18 to 24 December
inclusive.

Append-only is a deliberate design constraint, not a stylistic preference — see
`## Prior art and collisions`. Four pull requests are open against this repo and
one of them rewrites the base welcome text. An item that only *adds a clause*
survives all four; an item that restructures the sentence conflicts with each.

ex_chat owns the whole change: it composes the text, and its own bundled web
client renders whatever arrives without modification.

## Acceptance criteria

The seasonal clause is chosen by the current date, and exactly one of the three
forms applies on any date. Written as
`<base welcome> <space> <seasonal clause>`, where `<base welcome>` is whatever
the join greeting is on `master` at branch time.

Against `master` as it stands today, for room `default` and user `a-user`:

1. **Ordinary day** — on any date outside 18–25 December:
   `welcome to the default chat room, a-user! It is <n> days to Christmas 🎅`
   where `<n>` is whole days from today to the next 25 December.
   Test: `2026-09-08 → "It is 108 days to Christmas 🎅"`.
2. **Christmas Day** — on 25 December:
   `welcome to the default chat room, a-user! It is Christmas! Ho Ho merry Christmas 🎄`
   with **no** day count. Test `2026-12-25`, and `2027-12-25` to prove it is not
   a one-year special case.
3. **Shopping window** — on 18–24 December inclusive:
   `welcome to the default chat room, a-user! Ho ho a-user! Have you done your Christmas shopping yet? 🎁`
   with **no** day count. Tests: `2026-12-18` and `2026-12-24`, the two edges.
4. **Window boundary** — `2026-12-17` gives criterion 1 with `8 days`;
   `2026-12-18` gives criterion 3. This pair *is* the definition of where the
   window starts, and must be tested as a pair.
5. **Boxing Day rolls forward** — `2026-12-26 → "It is 364 days to Christmas 🎅"`.
   The count must never be `0` outside 25 December and never negative. Also test
   `2027-12-26 → "It is 365 days to Christmas 🎅"` — the leap-span case, since
   29 February 2028 falls inside it.
6. **The room and the name survive.** Appending preserves this for free, which
   is the point. A greeting that drops either has regressed.
7. **The date is injectable, and the suite does not depend on today.** Every
   assertion above is made against a pinned date. The suite must produce
   identical results run on any real date, including 25 December. A test that
   passes in September and fails at Christmas is the specific failure this
   criterion exists to prevent.
8. **The wire payload is unchanged** — still
   `{"room":"<room>","message":"<text>"}`, only the text differs.
   `priv/static/chat.html` needs no change; if it turns out to, report it rather
   than changing it here.
9. **Emoji arrive intact.** The acceptance test asserting the full payload must
   show the emoji surviving `Poison.encode!/1` and the WebSocket round trip, not
   a mangled or escaped sequence.

**If PR #29 merges before this item**, `<base welcome>` becomes
`<time-of-day greeting>, <user>! Welcome to the <room> chat room, <user>!` and
the expected strings in criteria 1–3 must be rebased onto it. The invariant this
item owns is the **seasonal clause**, not the sentence around it.

## Contract

**No cross-repo seam.** ex_chat declares `provides: []` and `consumes: []` in the
index and nothing else in the factory consumes it. This item depends on nothing
and blocks nothing.

The only interface that matters is internal, and it does **not** change:

```elixir
# ExChat.UserSessions.notify/2 — unchanged shape
UserSessions.notify(%{room: room, message: greeting_text}, to: user_id)
```

serialised by `Poison.encode!/1` in `ExChat.Web.WebSocketController` to:

```json
{"room": "default", "message": "welcome to the default chat room, a-user! It is 108 days to Christmas 🎅"}
```

`message` stays a single flat string. No new key, no structured date field, no
change to the join command or its error replies. Holding this shape fixed is why
this epic is one item in one repo and needs no client-side work.

### An implementation already exists on a branch

`issue-32-feat-days-to-christmas-...` is pushed to `origin` with **no open pull
request**, and carries `lib/ex_chat/welcome_message.ex`:

```elixir
defmodule ExChat.WelcomeMessage do
  def for_user(room, user_id, today \\ Date.utc_today()) do
    "welcome to the #{room} chat room, #{user_id}! " <> christmas_clause(user_id, today)
  end

  defp christmas_clause(user_id, today) do
    case days_to_christmas(today) do
      0 -> "It is Christmas! Ho Ho merry Christmas 🎄"
      days when days in 1..5 -> "Ho ho #{user_id}! Have you done your Christmas shopping yet? 🎁"
      days -> "It is #{days} days to Christmas 🎅"
    end
  end
  # ... days_to_christmas/1, next_christmas/1
end
```

This is already the append-only shape, already injects the date as a defaulted
argument, and already rolls forward past Christmas correctly. **The delta to the
approved requirements is one guard clause**: `days in 1..5` is a 20–24 December
window, and the approved window is 18–24 December, so it becomes `days in 1..7`.
Its tests need the same widening plus the boundary pair in criterion 4.

Prefer building on this branch over reimplementing it. If the operator would
rather start clean, the module name `ExChat.WelcomeMessage` should still be kept
— see the naming collision below.

Known wart, carried deliberately: the shopping clause names the user twice
(`welcome to the default chat room, a-user! Ho ho a-user! ...`). Fixing it means
restructuring the base sentence, which forfeits append-only and collides with
PR #29. Criterion 3 keeps the duplication. Overrule at gate 2 if the copy
matters more than the conflict.

## Approach

The greeting is currently a string interpolated inside the join use case
(`ExChat.UseCases.JoinChatRoom.on/2` on `master`, see the rename table above),
on the `:ok` branch of the room join. Composing three date-dependent forms there
would put date arithmetic inside a use case whose job is orchestration.

Extract composition into `ExChat.WelcomeMessage` — **pure**: given a room, a user
id and a date, it returns the text. The use case calls it and passes the result
to `UserSessions.notify/2` unchanged, so the use case's diff is one line. That
keeps date logic unit-testable across dozens of dates with no supervisor, no
registry and no WebSocket in the way, which is what makes criterion 7 cheap.

**On injecting the date** — the repo has an idiom for a test-controllable value:
`Application.get_env(:ex_chat, :ping_interval, @default_ping_interval)` in
`WebSocketController`, pinned via `Application.put_env/3` in the acceptance test.
That precedent is available, but prefer a defaulted argument
(`today \\ Date.utc_today()`), as the existing branch already does. `put_env` is
process-global, the acceptance test runs `async: true`, and a globally pinned
date would leak into every other test asserting a greeting.

**Expect to update existing assertions — there are ten.** The current greeting
string is hardcoded in:

- `test/ex_chat/use_cases/join_chat_room_test.exs` — lines 17, 29, 41, two of
  them `refute called` assertions carrying the full string.
- `test/ex_chat/web/websocket_acceptance_test.exs` — lines 37, 45, 46, 111, 122,
  123, 185, each asserting the complete JSON payload.

Every one becomes date-dependent unless the date is pinned. Updating them is part
of this item, and criterion 7 is not met until all ten are deterministic. Where
an acceptance test does not care about the season, matching on the base prefix
rather than the whole string keeps it stable — the existing branch already took
this approach in `test: match welcome message prefix in websocket acceptance tests`.

**The singular case is unreachable — do not write it.** With the window at 18–24
December the countdown can only render 8 through 365 days: 24 December sits inside
the shopping window, so `1 day` never renders, and neither do 2 through 7. Plural
`days` is therefore always correct, and a `1 day` branch would be dead code with a
test documenting behaviour no user can reach. Criterion 4 pins the boundary
instead. The PRD's constraint about reading "one day, not 1 days" is moot for this
reason — the chosen window answered it.

## Out of scope for this repo

- Any change to `priv/static/chat.html`. It renders the text it is given.
- Any change to the join command, the `already_joined` / `unexisting_room` error
  messages, authentication, or the access-token repository.
- Broadcasting the greeting to the room. It stays private to the joining user.
- The time-of-day greeting. That is PR #29's work, not this item's.
- The `Room`/`Rooms` rename. That is PR #25's work.
- Adding a date library. `Date` from the standard library covers all of this and

  test-only deps).
- A preference to disable seasonal greetings; per-user timezones; any holiday
  other than Christmas. All explicitly `Out` in the PRD.

### Decisions

- **Criteria 7 and 9 (the tension carried in the item log) resolved by *assert the
  alternation***, the only one of the three options that satisfies both as written.
  The new acceptance test asserts the complete payload against the three literal
  seasonal forms, so it is deterministic on every real date including 25 December,
  and the emoji are literal in the assertion. `Application.put_env/3` was rejected —
  process-global, and the suite is `async: true`. Criterion 9 was not overruled.
- **The alternation is asserted as two literal strings plus one metacharacter-free
  regex, not as a single alternation regex.** The first version used one regex
  containing `Have you done your Christmas shopping yet? 🎁`; the `?` is a regex
  metacharacter, so that pattern silently failed to match on 18–24 December — a
  test that passes in September and fails at Christmas, precisely the failure
  criterion 7 exists to prevent. Caught by the three-year sweep test, not by
  mutation testing, which cannot see a date-dependent hole when run in September.
- **The acceptance matcher change is additive.** `receive_matching/3` compared whole
  maps with `==`; it now delegates to `matches?/2`, which applies a predicate when
  given one and otherwise keeps exact equality. Every non-welcome assertion in the
  file is byte-for-byte unchanged in behaviour, which keeps the rebase against
  PRs #25, #29, #30 and #31 mechanical (finding 2 in the item log).
- **The two error-branch `refute called` assertions now refute the collaboration
  itself** — `UserSessions.notify(:_, :_)` — rather than carrying the old greeting
  string, which no longer exists anywhere and would have made them vacuously true.
  Verified non-vacuous by mutation.
- **The use-case unit tests stub `WelcomeMessage`** and assert the delegation, per
  `testing-principles.md`; recomputing the real greeting to build the expectation
  would have been tautological.
- **Built fresh rather than cherry-picking the prior-art branch** (`7f6e6ca`, which
  predates `33fc99f` and whose test changes no longer apply — item log finding 5).
  Its design was kept wholesale: the module name `ExChat.WelcomeMessage`, the
  append-only shape, the defaulted date argument. Its `days in 1..5` guard was
  widened to `days in 1..7`, which is exactly the approved 18–24 December window.
- **No `1 day` singular branch**, per the spec: with the window covering 24 December
  the countdown renders only 8–365 days, asserted directly by
  `"never counts zero or negative days to Christmas"` (min 8, max 365 over three years).
- **The shopping clause still names the user twice**, the wart the spec carries
  deliberately to preserve append-only.
